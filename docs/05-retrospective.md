# 项目复盘

## 最难的问题

难点在于保持模型决策、工具实际状态和费用账本一致。重规划和失败恢复时，旧产物、新估算与保存事务必须对应同一版本，否则容易少算费用或错误复用结果。

实现中由执行器维护账本与成功状态，模型负责选择动作。工具在状态副本上执行，最终与检查点同事务提交。计划更改时归档旧产物，保留已经发生的费用；生成前后采用不同的估算步骤，保证依赖关系可核对。

## 验证中的问题与改进

首次完整真实模型验收中，持续保存故障导致反复重试，停止时已使用 19 次调用。服务恢复后的第 20 次调用保存成功，但没有剩余额度执行 finish，任务返回 LIMIT_REACHED。

这一问题在离线 Mock 和合成 HTTP 测试中没有暴露。根据实际记录，错误反馈增加同计划失败次数，第二次失败标记 retryable=false；提示要求及时停止并保留产物，等待服务恢复后显式续跑。模型仍负责选择下一动作，执行上限没有提高或重置。

改进后14 个真实模型验收场景 14/14 通过，自动测试 51 项通过，独立费用审计通过。原始失败记录保留，便于比较改进前后的行为。

## 学习与取舍

判断 Agent 是否具备重规划能力，需要核对模型实际调用和工具结果。固定策略可以验证流程，但无法替代真实模型决策验证，因此 Mock、合成接口测试与真实模型运行记录分别保存。

原生工具循环足以支持本项目的规模，便于直接检查请求、动作、结果、账本和停止条件。暂不引入多 Agent、消息队列或图框架，减少实现与排查成本。

幂等需要分别覆盖请求、工具产物、记账与方案保存。本地事务可以保证本地状态一致，外部模型的 token 计费仍需按供应商规则单独核算。

## 限制与下一步

目前采用少量合成素材和规则表，尚未进行生成内容的独立人工质量评分或长期稳定性测试。下一步优先扩充主题和素材、引入内容质量评价，再考虑语义检索、多素材组合，以及外部收费工具的供应商幂等与对账。
